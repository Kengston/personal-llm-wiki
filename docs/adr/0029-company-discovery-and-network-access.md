# ADR-0029 — Discovery целевых компаний: сеть живёт в Node-слое моста (allowlist), движок остаётся без сети

> Расширяет [ADR-0015](0015-capture-write-path-permission-posture.md) (постура движка: `acceptEdits`, без shell, `deny: [WebFetch, WebSearch]`) и [ADR-0027](0027-incoming-multimodal-media.md) (недоверенный входящий контент сводится к тексту детерминированным Node-кодом). Уважает [ADR-0009](0009-tos-safe-engine-access.md) (ToS-безопасность, ordinary individual use), [ADR-0011](0011-relevance-sensitivity-filter.md)/[ADR-0013](0013-pii-density-valid-phones.md) (карантин, PII третьих лиц, `pii_density`), [ADR-0007](0007-engine-spawn-and-scheduler.md) (least-privilege, lethal trifecta), [ADR-0019](0019-knowledge-library-external-methodology.md)/[ADR-0020](0020-knowledge-library-fidelity-and-risk-tagging.md) (методология — чужие claims, не директива), [ADR-0003](0003-two-repos-public-private.md) (граница репо), [ADR-0024](0024-finance-reactive-dispatch.md) (интент → детерминированный диспатч), [ADR-0018](0018-finance-module.md) (append-only записи + pluggable провайдеры, `src/ingest/finance/fx.ts` как эталон контракта). Ничего не `superseded`.

**Контекст.** Подсистема «Поиск работы» опирается на методологию из `knowledge/job-search/` приватного репо ([ADR-0019](0019-knowledge-library-external-methodology.md)). Методология требует **точечного поиска**: одна тщательная заявка в 1–2 недели в заранее отобранную компанию, а не веерная рассылка. Отбор идёт по конкретным признакам: контракторов чаще берут стартапы, малый/средний продукт и аутсорс/аутстафф; «remote» ≠ удалёнка, потому что за словом часто стоит требование work permit, а настоящие маркеры — WFA / remote 100% / contractor; площадку проверяют по числу вакансий **и дате их создания** («нет даты — уходить»); вакансии $8k+ у источника приходили через нетворкинг и рефералы. Всё это — работа со **списком компаний**, которого сейчас нет ни в каком виде: список ведётся в голове и не переживает неделю.

Три факта делают решение дорого-обратимым и требуют ADR:

- **LinkedIn программно недоступен.** Скрейпинг и автоматизация нарушают ToS площадки, а методология прямо фиксирует: боты для рассылки → бан. Аккаунт LinkedIn — по той же методологии **основной канал** поиска; его потеря стоит дороже любой выгоды от автоматизации. Цена ошибки несимметрична, поэтому «аккуратно поскрейпить» — не компромисс, а ставка всем каналом.
- **Движок сознательно лишён сети.** `.claude/settings.json` в cwd движка задаёт `defaultMode: acceptEdits` + `deny: ["WebFetch","WebSearch"]` ([ADR-0015](0015-capture-write-path-permission-posture.md), пример — `wiki-example/.claude/settings.json`). Это не техническое ограничение, а митигация lethal trifecta: приватные данные в cwd + недоверенный контент + канал наружу не должны сходиться в одном процессе ([ADR-0007](0007-engine-spawn-and-scheduler.md)).
- **Значит, сеть нужна там, где нет LLM.** Задача ADR — зафиксировать, **где именно** проходит эта граница и какой контракт держит её сторона с сетью.

**Решение.**

### 1. Сеть — в детерминированном Node-слое моста, за allowlist доменов

Загрузчик — обычный TS-модуль моста (`src/bridge/net/fetcher.ts`), инструментом LLM он **не является**. Постура движка не меняется: `deny: [WebFetch, WebSearch]` остаётся, `--allowedTools` под сеть не расширяется. Эталон контракта — провайдеры `src/ingest/finance/fx.ts` ([ADR-0018](0018-finance-module.md)): узкий интерфейс, инъекция `fetchFn`, **никогда не бросает**.

Контракт загрузчика `fetch(url) → Promise<FetchedDoc | null>`:

- **Allowlist доменов.** Хост сверяется со списком (точное совпадение + явно разрешённые поддомены); всё остальное → `null` **без запроса**. Список — конфиг: в публичном репо только пример (`example.com`), рабочий — приватно/в env ([ADR-0003](0003-two-repos-public-private.md)).
- **Редиректы перепроверяются.** `redirect: 'manual'`, каждый `Location` заново проходит allowlist, максимум 3 перехода. Без этого allowlist обходится одним 302 — самая частая дыра такой схемы.
- **Только GET, только https, без учётных данных.** Ни cookies, ни `Authorization`, ни переиспользования чужой сессии — прямое следствие [ADR-0009](0009-tos-safe-engine-access.md) («никогда не реюзать токен/сессию в своём HTTP-клиенте»); правило распространяется на cookie-jar любой площадки, не только на подписочный OAuth.
- **Таймаут** — 10 с суммарно (`AbortSignal.timeout`), включая чтение тела.
- **Ретраи** — максимум один, только на сетевую ошибку/`5xx`/`429`, с бэкоффом (≥ 5 с, `Retry-After` уважается). `4xx` не ретраится никогда: повтор по 403 — это уже долбёжка.
- **Потолок размера** — 2 МБ, читаем потоково и **обрываем** на превышении (не `await response.text()` на неизвестном размере). `Content-Type` вне `{text/html, text/plain, application/json, text/csv}` → `null`.
- **User-Agent — честный и идентифицирующий**: имя личного инструмента + URL-плейсхолдер для связи. Мимикрия под браузер запрещена: она превращает вежливую загрузку в обход защиты, а обходов мы не делаем.
- **robots.txt уважается.** Перед первым обращением к хосту тянем `/robots.txt`, кешируем на процесс, применяем `Disallow` к нашему UA (и к `*`). `404`/пустой файл → разрешено; недоступен по сети или `5xx` → **считаем запрещённым** (fail-closed по вежливости, не по безопасности).
- **Rate-limit** — не чаще 1 запроса в 2 с на хост и не более 20 запросов на хост за прогон; обход **последовательный**, никаких параллельных вееров.
- **Никогда не бросает.** Любая ошибка (сеть, таймаут, allowlist, robots, размер, тип) → `null` + строка в лог. Discovery-ход деградирует («из подключённых источников доступно 2 из 3»), мост не падает.
- **Логи без содержимого и без query.** Пишем host, статус, размер, причину отказа. Ни тело, ни полный URL с query-параметрами (запрет на PII в query — сквозной).
- **Тесты офлайн.** `fetchFn` инъектируется (как в `CbrFxProvider`); живой сети в тестах нет, фикстуры синтетические.

### 2. Три канала ввода и риск каждого

Это ровно три значения `company_source` (решение владельца D4): `manual`, `linkedin_export`, `web_search`. Канал хранится на каждой записи — иначе покрытие (§7, D11) не посчитать честно.

**(а) Ручной ввод через Telegram** (`company_source: manual`)**.** Владелец диктует компанию/вакансию, движок эмитит интент-блок, мост детерминированно диспетчеризует его в чистые функции — тот же паттерн, что у финансового модуля ([ADR-0024](0024-finance-reactive-dispatch.md)). Риск: опечатки и дубли («Acme» / «Acme Inc» / «ACME»). Митигация: дедуп по нормализованному **домену сайта**, а не по названию; при коллизии — вопрос владельцу кнопками, а не молчаливый мёрдж.

**(б) Импорт официального экспорта данных LinkedIn (файлом)** (`company_source: linkedin_export`)**.** Легальный, ToS-safe путь: площадка сама отдаёт архив по запросу владельца — ни скрейпинга, ни автоматизации. Риск — **плотность PII**: ось A фильтра карантинит документ **целиком** при `pii_density ≥ 5` ([ADR-0011](0011-relevance-sensitivity-filter.md)/[ADR-0013](0013-pii-density-valid-phones.md)), а любой экспорт связей — это сотни email и телефонов. Импорт «одним файлом» гарантированно уедет в `raw/.quarantine/` и не доедет никуда.

> **Правило импорта: одна компания = одна запись.** CSV разбирается детерминированным Node-парсером **до** классификации; наружу идут отдельные записи-организации, каждая классифицируется и пишется самостоятельно. Контактные поля третьих лиц отбрасываются **на парсинге** (см. §5), а не «зачищаются потом». Файл связей (`Connections.csv`) как знание **не импортируется вовсе**: из него берётся максимум производный булев факт «в компании есть тёплый контакт», без персоналий.

**(в) Веб-поиск по публичным источникам** (`company_source: web_search`)**.** Карьерные страницы компаний, открытые job-борды, публичные подборки — только через загрузчик из §1. Риск: подборки протухают (методология прямо отмечает, что GitHub-списки remote-компаний «загораются и потухают»), а страница вакансии живёт неделями. Митигация: каждая запись несёт `fetched_at` и `source_url`; свежесть — **поле в данных**, а не вера в источник; отсутствие даты публикации у площадки само по себе фиксируется как сигнал низкого доверия (методология: «нет даты — уходить»).

**Чего в каналах нет и не будет:** авторизованного скрейпинга, парсинга за логином, headless-браузера под площадки с ToS-запретом, автоматической рассылки откликов и коннектов. Система **готовит и ранжирует**, отправляет человек.

### 3. Модель данных: `company`, `opportunity`, провенанс

**`company`** — стабильная сущность (леджер `companies.jsonl`). `id` — человекочитаемый стабильный slug, производный от нормализованного домена; **ключ дедупа — по-прежнему `site_domain`**, а `id` — то, на что ссылаются `opportunity.company_id` и `application.company_id` ([ADR-0030](0030-jobsearch-funnel-reporting.md)): дедуп и ссылка — разные роли, и склеивать их в одно поле нельзя (домен у компании может смениться, ссылки при этом не должны рваться). Критерии оценки взяты из методологии и хранятся **не булевыми, а трёхзначными** (`yes | no | unknown`):

| Поле | Значения | Откуда |
| --- | --- | --- |
| `company_type` | `startup`, `product_smb`, `product_enterprise`, `outsourcing_outstaff`, `agency`, `unknown` | методология: контракторов чаще берут стартапы/малый-средний продукт/аутсорс |
| `stage` | `bootstrapped`, `seed`, `series_a`, `series_b_plus`, `public`, `unknown` | публичные источники |
| `remote_mode` | `wfa`, `remote_100`, `remote_country_bound`, `hybrid`, `onsite`, `unknown` | маркеры WFA / remote 100% |
| `hires_contractors` | `yes`/`no`/`unknown` | текст вакансии + разговор |
| `work_permit_required` | `yes`/`no`/`unknown` | **только разговор даёт факт** (см. ниже) |
| `interview_language` | `en`, `ru`, `other`, `unknown` | вакансия/разговор |
| `hq_country`, `timezone_overlap` | строка / `unknown` | публичные источники |
| `has_warm_contact` | `yes`/`no`/`unknown` | нетворкинг владельца |
| `hiring_status` | `active`, `paused`, `unknown` | наблюдение |

Каждое значимое поле — не голое значение, а `{ value, source, confirmed_by_human: boolean, confirmed_at: ISO|null }`. Разница между «так написано в вакансии» и «так сказал человек» — не косметика, а основа отсева.

> **`work_permit_required` — особый случай.** Методология прямо говорит: точно понять, требуется ли разрешение на работу, **можно только в разговоре с HR** — публично «work from anywhere» пишут единицы. Поэтому: (1) значение, извлечённое из текста вакансии, всегда `confirmed_by_human: false` — это гипотеза; (2) состояние `unknown` — **легальное и частое**, оно **не отсеивает компанию** (иначе система выбросит ровно тот класс компаний, о которых методология говорит «узнаётся только в диалоге»); (3) факт появляется только после разговора — тогда проставляются `confirmed_by_human: true` и `confirmed_at`.

**`opportunity`** — конкретная вакансия/зацепка (у одной компании их много во времени; леджер `opportunities.jsonl`): `id`, `company_id`, `title`, `source_url`, `external_id`, `posted_at` (nullable — отсутствие даты информативно), `fetched_at`, `employment_type` (`contract`/`employee`/`unknown`), `remote_mode`, `company_source` (`manual`/`linkedin_export`/`web_search` — **откуда узнали** о компании/вакансии), `raw_ref` (путь к иммутабельному снапшоту в `raw/jobsearch/`).

> **Воронки в `opportunity` нет.** Стадия отклика, причина отсева и всё, что происходит ПОСЛЕ подачи, целиком принадлежит [ADR-0030](0030-jobsearch-funnel-reporting.md): там стадия не хранится полем вообще, а вычисляется fold'ом по `application_events.jsonl`, и словарь стадий существует ровно один. Полей `funnel_stage`/`dropped_reason` здесь нет и не заводится — иначе у одного процесса появляется второй словарь состояний, который разъедется с первым при первой же правке.
>
> **Про имя `channel`.** Слово означало сразу две разные вещи — «откуда узнали о компании» и «как подан отклик» — и уже развело документы. Поэтому: канал **добычи** везде `company_source` (`manual`/`linkedin_export`/`web_search`, три канала §2), канал **подачи** везде `submission_channel` (`referral`/`direct`/`inbound`, живёт в `applications.jsonl`, [ADR-0030](0030-jobsearch-funnel-reporting.md)). Поля с именем `channel` в схемах подсистемы нет.

**Провенанс** — обязателен у каждой записи: `company_source`, `source_url` (без query), `fetched_at`, `content_sha256`, `parser_version`, `robots_ok`. Запись без провенанса неотличима от галлюцинации движка и в `wiki/` не промоутится.

Хранение: сырьё → иммутабельный `raw/jobsearch/<host>/<sha>.md` через `failClosedSanitize` ([ADR-0015](0015-capture-write-path-permission-posture.md) §2); структурированные записи — append-only JSONL **там же, в приватном `raw/jobsearch/`**: `companies.jsonl` и `opportunities.jsonl` лежат рядом с `applications.jsonl`/`application_events.jsonl` воронки ([ADR-0030](0030-jobsearch-funnel-reporting.md)) и пишутся тем же параметризованным `Ledger` (параметризация каталогом и картой схем — слайс [ADR-0028](0028-career-data-module.md), «Следствия»). В `wiki/` идут **только человеческие заметки прозой** — структурированные записи туда не промоутятся, это контент-модель [ADR-0010](0010-wiki-content-model.md) и append-only-инвариант [ADR-0018](0018-finance-module.md), а не вопрос удобства. Методология остаётся в `knowledge/` ([ADR-0019](0019-knowledge-library-external-methodology.md)) и в схему **не копируется**.

Два жёстких запрета в схеме:

- **Полей под фиктивные места работы нет и не будет.** Приём «компании-доноры» для подмены мест работы остаётся в `knowledge/` с тегом `risk: grey` как методология источника ([ADR-0020](0020-knowledge-library-fidelity-and-risk-tagging.md)), но инструментальной поддержки в коде и схеме не получает.
- **Контакты владельца (телефон, почта, ссылка на профиль) в репо не хранятся** — в данных только ключи-плейсхолдеры, реальные значения подставляются при рендере из gitignored-файла/env.

### 4. Скоринг: гейты отсекают, ручной вес ранжирует

Два разделённых механизма, которые нельзя смешивать в одно число.

**Гейты — булевы, из методологии, применяются только к известным значениям:**
- `hires_contractors == no` → отсев;
- `remote_mode == onsite` → отсев;
- `work_permit_required == yes` → отсев (при выбранной владельцем стратегии локации; методология даёт три, «изображать местного» помечена `risk: grey` и **не автоматизируется**);
- `posted_at` старше порога свежести → отсев вакансии (не компании);
- дата публикации отсутствует → флаг «низкое доверие площадке», **не** автоотсев.

**`unknown` не отсеивает никогда.** Это правило важнее любого гейта: неизвестность — состояние ожидания разговора, а не отказ.

**Ранжирование — ручной вес владельца** (поле `fit_rank`, целое 0–5, ставится кнопками в Telegram) **плюс перечисление подтверждённых фактов**: сколько критериев `confirmed_by_human`, есть ли тёплый контакт/реферал (методология: все вакансии $8k+ шли через нетворкинг или реферал), насколько свежа зацепка.

**Запрещено выдумывать числовые веса, которых нет в методологии.** «Стартап = 0.7, аутсорс = 0.4, remote_100 = +0.15» — ложная точность: источник даёт **порядок предпочтения и булевы признаки**, а не коэффициенты, и проверить такой composite score не против чего. Поля-«вердикта» вроде `fit_score` в схеме нет и не появится: `fit_rank` — это то, что владелец **поставил**, а не то, что система **вывела**. Сортировка обязана объясняться строкой из сработавших фактов («вес 4 · контрактор подтверждён в разговоре · есть тёплый контакт · вакансия 3 дня»), а не непрозрачным баллом.

### 5. PII третьих лиц

**Храним:** роль (`CTO`, `HR`, `hiring manager`, `engineer`), ссылку на **публичный** профиль, дату и канал контакта, привязку к компании, краткий факт договорённости. Это минимум для follow-up.

**Не храним никогда:** личные email и телефоны, мессенджер-хендлы, адреса, переписку как есть, экспорт связей LinkedIn.

Ось A фильтра ([ADR-0011](0011-relevance-sensitivity-filter.md)) применяется к **каждой записи** отдельно; при срабатывании `others_pii` запись целиком уходит в карантин — «подчистить и оставить» нельзя. **Санитайзер при этом не ослабляется.** Причина конкретная: `failClosedSanitize` маскирует всё, что похоже на телефон (10–15 цифр), и портит соседние данные молча — ИНН и числовой id вакансии в URL превращаются в `[REDACTED:phone]` (проверено на правиле `phone` в `src/ingest/sanitizer.ts`). Отсюда практическое следствие для схемы: **числовые идентификаторы хранятся склеенными с буквенным префиксом без разделителя** (`li4021234567`, а не `li-4021234567` и не голое число) — negative lookbehind `(?<![\w.])` тогда не срабатывает и id переживает write-path. **Правило префикса действует только для id, попадающих в САНИТАЙЗИМЫЙ СВОБОДНЫЙ ТЕКСТ** — сырьё в `raw/`, заметки, `reason_note`. Типизированные поля JSONL (`external_id`, `source_url`, `vacancy_ref`) санитайзер не проходят вовсе ([ADR-0030](0030-jobsearch-funnel-reporting.md), «Инварианты»: `failClosedSanitize` — только к свободному тексту), и там идентификатор хранится как есть. Две митигации не конкурируют и не дублируют друг друга: одна про текст, другая про границу ответственности схемы. Правильный ответ на такое поведение маскера — держать PII **вне** данных (плейсхолдеры + подстановка при рендере), а не расслаблять правила.

### 6. Prompt-injection: чужой текст — это данные, не промпт

Текст вакансии, карьерной страницы и импортированного файла — **недоверенный вход** ([ADR-0027](0027-incoming-multimodal-media.md)). Обеспечение:

1. **Загруженный документ целиком в промпт не попадает никогда.** Извлечение делает детерминированный парсер на Node (HTML → текст → правила/regex → типизированные поля). LLM в разборе не участвует.
2. **В контекст движка идут только типизированные значения** из фиксированного набора полей §3: enum'ы, даты, домен, короткие строки с жёстким лимитом длины и прогнанные через `stripInvisible` (обфускация zero-width/bidi не проедет).
3. **Сырьё оседает в `raw/jobsearch/<host>/<sha>.md`** через `failClosedSanitize`, с `source_class: web:untrusted`, и подчиняется обычным правилам чтения `raw/` ([ADR-0011](0011-relevance-sensitivity-filter.md)).
4. **Практический результат:** абзац «Ignore previous instructions and …» на карьерной странице попадает в raw-файл и **не** попадает в промпт — движок увидит `remote_mode: unknown`, а не текст.
5. **Lethal trifecta закрыта с двух сторон:** недоверенный контент к движку не поступает, а у движка нет канала наружу (сети нет по [ADR-0015](0015-capture-write-path-permission-posture.md)). Ослабление любой из сторон требует отдельного ADR.
6. **Если парсер не справится** и понадобится LLM-извлечение из сырого текста — это отдельный ADR-аддендум с изоляцией хода (пустой cwd без приватного репо, выход — только JSON, валидируемый по схеме, без права записи). В v1 не делаем.

### 7. Явные ограничения (называть вслух, не обещать лишнего)

- **«Все подходящие компании» = все из подключённых источников.** Полного покрытия рынка не существует и обещать его нельзя. Формулировки бота обязаны это отражать: «из подключённых источников найдено N», а не «найдены все».
- **Корпоративный MCP-хаб работодателя расширять или редактировать под личные задачи запрещено.** Инфраструктура принадлежит компании; личный discovery целиком живёт в личном репо и личном мосте. Это не техническое ограничение, а граница собственности.
- **Никакой автоматизации откликов и коннектов** — методология однозначна (боты → бан), [ADR-0009](0009-tos-safe-engine-access.md) требует ordinary individual use.
- **Бюджет.** Сеть дешёвая, Agent-SDK-кредит — нет ([ADR-0009](0009-tos-safe-engine-access.md)). Конкретно: discovery — **один пакетный прогон в сутки**, routine `jobsearch-discovery` в scheduler (рядом с digest-sweep, [ADR-0007](0007-engine-spawn-and-scheduler.md)); за прогон — не более 3 хостов и не более 20 запросов на хост (§1, rate-limit там же); ход движка в прогоне **один** и получает уже извлечённые типизированные поля, а не страницы. Discovery на входящее сообщение не запускается никогда — ручной ввод (канал «а») сети не требует.

**Альтернативы (отвергнуты).**

- **Снять `deny: [WebFetch, WebSearch]` с движка** — «пусть сам поищет». Отвергнуто: это ровно lethal trifecta ([ADR-0007](0007-engine-spawn-and-scheduler.md)) — приватная вика в cwd + недоверенный контент из сети + исходящий канал в одном процессе. Плюс потеря детерминизма: allowlist, robots, rate-limit и потолок размера проверить нечем, решение «что скачать» принимает модель, а инъекция со страницы становится инструкцией.
- **Скрейпинг LinkedIn** (авторизованный, через cookie-сессию, через обходы). Отвергнуто: нарушение ToS и риск бана аккаунта, который по методологии и есть главный канал; выгода мелкая, потеря — весь канал. Легальная замена — официальный экспорт данных владельца файлом (канал «б»).
- **MCP-сервер в корпоративном хабе работодателя** (готовая инфраструктура, OAuth, деплой, роли). Отвергнуто: чужая инфраструктура под личную задачу; вдобавок личные данные поиска работы утекли бы в корпоративный периметр. Личная подсистема не касается корпоративного хаба вообще.
- **Headless-браузер (Playwright) для рендера SPA-вакансий.** Отвергнуто для v1: тяжёлая зависимость, и для площадок с ToS-запретом рендер неотличим от скрейпинга. Если страница не отдаёт HTML — канал (в) просто возвращает `null`.
- **Общая таблица «компания + вакансия».** Отвергнуто: у компании много вакансий во времени, критерии живут на компании, а воронка — на `opportunity`; слияние ломает и дедуп, и отчётность.
- **Composite score из весов критериев.** Отвергнуто (см. §4): весов в методологии нет, число невозможно объяснить и не с чем сверить.
- **Хранить контакты рекрутеров «для удобства follow-up».** Отвергнуто: PII третьих лиц, карантин по оси A, нулевая необходимость — роль + публичный профиль + дата контакта покрывают follow-up полностью.

**Следствия.**

- Новый модуль загрузчика в слое моста (`src/bridge/net/fetcher.ts`: allowlist, редиректы, robots, rate-limit, потолок размера, «не бросает») и новый ingest-модуль под схему/парсеры/дедуп (`src/ingest/jobsearch/companies.ts` — zod-схемы `company`/`opportunity` + парсеры + дедуп по `site_domain`). Каталог модуля общий с воронкой ([ADR-0030](0030-jobsearch-funnel-reporting.md)): `src/ingest/jobsearch/`, без дефиса. Постура движка и `.claude/settings.json` **не меняются**.
- Классификатор получает новые `source_class`: `web:untrusted`, `linkedin:export`.
- Allowlist доменов: в публичном репо — только пример-конфиг с `example.com`; рабочий список приватно ([ADR-0003](0003-two-repos-public-private.md)). `pnpm lint:public` обязан оставаться зелёным.
- Тесты — офлайн, на швах: инъекция `fetchFn`; редирект за пределы allowlist → `null`; `Disallow` в robots → `null`; превышение потолка размера → `null`; импорт с 5+ PII в файле → покомпанийные записи, ни одна не тащит контакты; `work_permit_required: unknown` не отсеивается гейтом; id вакансии переживает `failClosedSanitize`.
- Оговорка о покрытии (§7, D11) — **одна строка-шаблон в коде**, а не редполитика: `sourceCoverageLine(connectedSources)` рядом с генератором ответа собирает единственную допустимую формулировку («из подключённых источников (N: …) найдено M»), и тест проверяет, что она перечисляет подключённые источники и не содержит «все»/«весь рынок». Свободных формулировок покрытия в промпте нет — «ревьюить текст» становится нечего.
- Индекс [docs/adr/README.md](README.md) пополнен строкой 0029 отдельным ходом (файл общий, правится вне этого ADR).
