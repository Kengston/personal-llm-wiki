# ADR-0035 — Единственный путь записи в леджер: CLI движка с валидацией перед append

> Уточняет [ADR-0018](0018-finance-module.md) (принцип «валидация перед записью» в `Ledger.append`) и [ADR-0030](0030-jobsearch-funnel-reporting.md). Закрывает класс дефекта, который [ADR-0031](0031-hh-channel.md) §1 считал закрытым.

**Контекст.** Класс `Ledger` валидирует каждую запись zod перед `appendFileSync`. Но скилл `jobsearch-run` описывал второй путь: «прямая запись JSONL, когда работает агент», а валидацию схемой как отдельный шаг после записи. 02.09 в 18:30 один агентский прогон дописал 32 записи в `companies.jsonl` и 34 в `applications.jsonl` мимо схемы (одинаковые `fetched_at` и `parser_version`); `readAll()` их молча пропускает с warn в stderr, воронка недосчитывает 7,8 %. Формулировка «после записи валидировать» уже провалилась один раз; усиливать её бессмысленно.

**Решение.**

1. В движке появляются `pnpm jobsearch:append -- <ledger>` (строки из stdin или файла; каждая валидируется zod до записи; пачка всё-или-ничего; печатает readback) и `pnpm jobsearch:validate` (все леджеры, exit 1 при любом пропуске). `form-answers.jsonl` получает схему и входит в спецификацию леджера.
2. Скиллы описывают запись одним способом: командой CLI. Инструкции о прямом дописывании строк из скиллов убираются, чтобы способ обойти валидацию не лежал в контексте агента.
3. `jobsearch:validate` входит в lint хранилища; зелёный lint = ноль пропущенных записей.

**Рассмотрено и отвергнуто.** Запись только через мост и Telegram-интент: блокирует агентский прогон, который сейчас основной способ работы. Оставить прямую запись и «усилить формулировку»: уже не сработало.

**Следствия.** Агентский прогон должен иметь собранный движок (`dist/`), как и `jobsearch:report`. Учебный журнал ([ADR-0034](0034-learning-contour.md)) пишется тем же путём: `pnpm learn:append`.
