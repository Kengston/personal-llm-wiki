# ADR-0028 — Модуль данных карьеры: append-only леджер, метрики-плейсхолдеры, EN/RU без фолбэка

> Кристаллизовано гриллингом (2026-08-02). Первая из трёх частей подсистемы «Поиск работы» (конструктор резюме; discovery компаний и отчётность по воронке — отдельными ADR). Наследует форму данных [ADR-0018](0018-finance-module.md) (append-only JSONL + zod), границу репо [ADR-0003](0003-two-repos-public-private.md), контент-модель [ADR-0010](0010-wiki-content-model.md), write-path-постуру [ADR-0015](0015-capture-write-path-permission-posture.md), кнопочный шов [ADR-0023](0023-telegram-transport-media-and-callbacks.md)/[ADR-0024](0024-finance-reactive-dispatch.md)/[ADR-0026](0026-finance-proactive-and-callbacks.md).
>
> Все примеры синтетические. Реальные данные карьеры владельца — в приватном `llm-wiki-content/raw/career/`; здесь только схема и правила.

**Контекст.** Факты о профессиональном опыте сегодня живут прозой: `wiki/projects/` (accomplishment-записи, [ADR-0010](0010-wiki-content-model.md) §3.5), деривативный `wiki/capability-profile.md`, снапшот `scripts/career-evidence.sh` в `raw/career/`, плюс черновики резюме на EN и RU. Одно и то же число («столько-то репозиториев», «сокращение времени сборки на столько-то процентов») физически скопировано в четыре-пять мест и расходится при каждой пересборке: свободный текст не знает, что где-то есть ещё одна его копия. У числа в прозе нет ни даты, ни источника — на вопрос «откуда цифра?» ответить нечем. Собрать версию резюме под конкретную вакансию можно только руками: перечитать страницы, выбрать релевантное, перевести, уложить в формат. Прозаический слой в этом не виноват — он сознательно про «что я умею», а не машинная форма; ему нужен сосед, а не переделка.

**Решение.**

- **Append-only JSONL-леджер + zod-схемы по образцу финансового модуля.** Данные — в приватном репо `raw/career/*.jsonl` (по файлу на сущность); схемы — в публичном `src/ingest/career/types.ts`. Механика — та же, что в [`src/ingest/finance/ledger.ts`](../../src/ingest/finance/ledger.ts): path-allowlist guard (запись только под приватный `raw/`, никогда под корень публичного репо), zod-валидация ДО записи, `readAll` пропускает битые строки с warn. Не SQL и не вектор ([ADR-0002](0002-no-embedder-pure-karpathy.md)) — леджер обязан читаться git-diff'ом построчно.
- **Правка = новая строка.** Редактирование характеристик идёт кнопками в Telegram (интент-протокол + диспетчер + callbacks по образцу [ADR-0024](0024-finance-reactive-dispatch.md)/[ADR-0026](0026-finance-proactive-and-callbacks.md)), а бот пишет только append: изменение — новая запись с тем же `id` и большим `ts` (last-wins у читателя), удаление — запись с `deleted: true` (tombstone). Через бота ходит СТРУКТУРА: добавить/удалить запись, включить/исключить в варианте, порядок, статусы, короткие поля. Длинные тексты (`profile.about`, формулировка достижения) владелец диктует, движок формулирует и показывает на подтверждение — записывается подтверждённое.
- **Сущности.** Общие конвенции: `id` — человекочитаемый стабильный slug (он же ездит в компактном callback-payload ≤64 байт, [ADR-0026](0026-finance-proactive-and-callbacks.md)); `ts` — ISO-8601 момент записи; даты периодов — `YYYY-MM` (месячная точность, день в резюме не нужен и не хранится); текстовые поля — `i18nText` (см. ниже).

  | Сущность | Поля |
  |---|---|
  | `profile` | `id`, `headline` (i18n), `about` (i18n, длинный текст), `location` (город/страна, не адрес), `work_setup` (`onsite`/`hybrid`/`remote` + готовность к релокации), `contact_keys[]` (ссылки на `contact.key`), `ts` |
  | `position` | `id`, `org_key` (непрозрачный ключ организации; отображаемое имя — в приватном справочнике, не в публичной схеме), `title` (i18n), `employment` (`full_time`/`contract`/`part_time`/`freelance`), `started_at`, `ended_at` (пусто = по настоящее время), `skill_ids[]`, `summary` (i18n, одна-две фразы), `order`, `ts`, `deleted` |
  | `achievement` | `id`, `position_id` **или** `project_id`, `text` (i18n, содержит плейсхолдеры `{{metric.key}}`), `metric_keys[]` (денормализация текста — для валидатора и скоринга), `skill_ids[]`, `impact` (грубая рубрика: `shipped`/`scaled`/`saved`/`led`/`fixed`; опц.), `order`, `ts`, `deleted` |
  | `metric` | `key` (стабильный, `[a-z0-9_.-]`, он же в плейсхолдере), `value` (число), `unit` (свободная строка — `pct`, `count`, `ms`, `x`, `months`, валюта; захардкоженного перечня нет, как у `currency` в [ADR-0018](0018-finance-module.md)), `display` (i18n, опц. — когда показывать надо формулировкой, а не сырым числом), `as_of` (дата, к которой число относится), `source` (`evidence`/`business`/`manual`), `evidence_ref` (`snapshot_id` + путь, только для `evidence`), `verifiable` (bool, обязателен при `business`), `note`, `ts` |
  | `skill` | `id`, `name` (i18n; для технонимов — `no_translate: true`), `kind` (`language`/`framework`/`tool`/`domain`/`practice`/`soft`), `level` (`core`/`working`/`familiar`), `first_used`, `last_used`, `ts`, `deleted`. «Лет опыта» — ВЫЧИСЛЯЕМОЕ (из `first_used`/`last_used` и позиций), отдельным полем не хранится: это ровно тот дрейф, от которого мы уходим |
  | `education` | `id`, `institution_key`, `program` (i18n), `degree` (опц.), `kind` (`degree`/`course`/`certification`), `started_at`, `ended_at`, `credential_key` (опц. — ключ, не URL; см. `contact`), `ts`, `deleted` |
  | `language` | `id` (ISO-639-1), `level` (CEFR или `native`), `ts` |
  | `project` | `id`, `name` (i18n), `role` (i18n, опц.), `summary` (i18n), `started_at`, `ended_at`, `skill_ids[]`, `link_key` (опц., ключ), `wiki_ref` (relative-путь на `wiki/projects/<slug>.md`), `ts`, `deleted`. `wiki_ref` — единственная связь машинного слоя с прозой: ссылка, не копия |
  | `variant` | `id`, `lang`, `target` (`role_family`, `seniority`, `keywords[]` — из текста вакансии детерминированным парсером), `pins[]` (принудительно включить), `excludes[]` (принудительно исключить), `form` (`max_pages`, `max_bullets_per_position`, `max_detailed_positions`), `evidence_version` (пин к `snapshot_id`), `status` (`draft`/`active`/`archived`), `ts`. Статуса отклика здесь НЕТ — воронка ссылается на `variant.id` своим полем `application.variant_id` в `applications.jsonl` ([ADR-0030](0030-jobsearch-funnel-reporting.md)) |
  | `contact` | `key` (напр. `email_primary`, `profile_public`), `kind` (`email`/`phone`/`url`/`messenger`), `label` (i18n, опц.), `render_required` (bool), `ts`. **Значения нет ни в одном поле схемы** |

- **Контакты — только ключи, значения подставляются при рендере.** Реальные телефон/почта/ссылка на профиль живут в gitignored-файле (`contacts.local.json`/env) и попадают только в отрендеренный документ, который лежит вне обоих репозиториев. Причина не в аккуратности, а в механике: write-path обязан проходить `failClosedSanitize` ([rules.md §2](../../compiler/rules.md)), который маскирует PII И ПОРТИТ СОСЕДНИЕ ДАННЫЕ молча — проверено, что номер налогоплательщика и цифровой идентификатор вакансии внутри URL уезжают в `[REDACTED:phone]`. Санитайзер НЕ ослабляем: ослабление ради удобства резюме открывает дыру на всём write-path вики. Тот же механизм ключей — для любой внешней ссылки, идентифицирующей владельца (публичный профиль, верификация сертификата).
- **Числа не пишутся в текст достижения.** `achievement.text` содержит плейсхолдеры `{{metric.key}}`; значение живёт ровно в одной записи `metric`. Обоснование прямое: одно и то же число сегодня существует в резюме EN, резюме RU, `capability-profile` и на странице проекта — четыре копии, которые расходятся при первой же пересборке, потому что обновляют одну. С плейсхолдером обновление метрики автоматически докатывается во все варианты, а у числа появляются `as_of` и `source` — есть что ответить на «откуда цифра». Валидатор: плейсхолдер без `metric` → `unknown_metric` (рендер fail-closed, документ с `{{…}}` внутри не выдаётся); числоподобный литерал в тексте (проценты, разрядные группы, кратности) → предупреждение `literal_number_in_text` — эвристика, не блокирует, иначе она воюет с «HTTP/2» и версиями библиотек.
- **`metric.source` — три класса происхождения.** `evidence` — импортировано машинно из снапшота [`scripts/career-evidence.sh`](../../scripts/career-evidence.sh) (коммиты, объём кода, даты, стек); руками не редактируется — несогласие оформляется отдельной записью класса `business`/`manual`. `business` — бизнес-эффект, вводится руками; обязательны `as_of` и `verifiable` (можно ли подтвердить внешне: дашборд, релиз-нот, письмо) — непроверяемое число в резюме опаснее его отсутствия. `manual` — всё остальное (оценки, приблизительные), в дефолтный набор варианта не попадает без явного пина.
- **EN/RU: факт языконезависим.** Даты, `metric.value`, `skill.kind`, связи — одни на все языки; переводится ТОЛЬКО листовое текстовое поле. Форма — `i18nText` как словарь `{ <lang>: string }` со свободным ключом языка (новый язык не требует правки схемы — тот же приём, что `currency` в [ADR-0018](0018-finance-module.md)). Отсутствующий перевод при рендере варианта → ошибка валидатора `missing_translation` со списком `id` + поле, НЕ молчаливый фолбэк на другой язык: русский буллет посреди английского резюме — худший дефект документа из возможных, и он ровно тот, который тихий фолбэк производит. Осознанное исключение — `no_translate: true` на поле (техноним), тогда одно значение используется во всех языках явно.
- **Таргетирование под вакансию — скоринг + пины/исключения.** Скоринг детерминированный, на Node-слое: пересечение `skill_ids`/`keywords` вакансии, свежесть (`last_used`, `ended_at`), рубрика `impact`, наличие проверяемой метрики. Пины и исключения варианта — жёсткий оверрайд поверх скоринга: машина предлагает порядок, решает владелец. **Ограничения формы (одна страница, 3–5 буллетов, максимум 3 детальных места работы) — свойство РЕНДЕРА, а не данных:** леджер хранит всё, рендер режет по хвосту скоринга и ОБЯЗАН вернуть список выброшенного с причиной (`cut_by_score` / `cut_by_form_limit`), который мост показывает в Telegram. Молча выпавшее сильное достижение — это скрытая потеря, а не аккуратная вёрстка.
- **Воспроизводимость.** `variant.evidence_version` пинится к `snapshot_id` того снапшота evidence, из которого взяты метрики. Если появился более новый снапшот и он меняет значение хотя бы одной использованной метрики — при рендере предупреждение `evidence_stale` со списком расхождений; рендер НЕ блокируется: уже отправленный вариант должен воспроизводиться как есть. Обновление — это новый вариант с новым пином, а не переписывание старого.
- **Схема не поддерживает фиктивные места работы.** `position.org_key` ссылается на реальную организацию; полей под подменные/«донорские» компании нет, генератор и подборщик доноров не реализуются. Знание об этом приёме остаётся в `knowledge/job-search/` с тегом `risk: grey` как описание чужого метода ([ADR-0019](0019-knowledge-library-external-methodology.md)/[ADR-0020](0020-knowledge-library-fidelity-and-risk-tagging.md)) — но `risk:`-механика принадлежит категории внешней методологии и в леджер карьеры не переносится: описывать приём и инструментально его поддерживать — разные вещи.
- **Сеть — не здесь.** Импорт официального экспорта данных LinkedIn — файлом (площадку называем прямо: её имя — не персональные данные, а канал `company_source: linkedin_export` в схеме [ADR-0029](0029-company-discovery-and-network-access.md)); сетевые каналы (веб-поиск источников) живут в Node-слое моста с allowlist доменов, движок (`claude -p`) остаётся без сети. Чужой текст парсится детерминированным кодом в типизированные поля.

**Альтернативы (отвергнуты).**

- *Markdown + frontmatter прямо в существующих страницах `wiki/projects/`.* (1) Ломает контент-модель [ADR-0010](0010-wiki-content-model.md): страница — проза «что предметно сделал», а массивы достижений и метрик превращают её в структурированную выгрузку, против которой правило сжатия и написано. (2) Гранулярность не та: достижение принадлежит ПОЗИЦИИ и переиспользуется в нескольких вариантах, а страница — одна на проект. (3) Кнопочная правка означала бы построчный патч YAML внутри прозы — движок перезаписывает страницу целиком вместо append, а это ровно error-propagation из [rules.md §0](../../compiler/rules.md). (4) Нет истории: как выглядела формулировка в отправленном отклике — не восстановить. Связь сохраняем ссылкой `project.wiki_ref`, дублирование не заводим.
- *Один YAML-файл, правится руками.* Правка целиком: одна ошибка движка или бота переписывает весь профиль; конкурентная правка из Telegram и из редактора — конфликт всего файла вместо append одной строки; истории нет; кнопочный CRUD требует адресной записи одной сущности.
- *Числа прямо в тексте достижения.* Это статус-кво, и именно он породил расхождение: текст существует в нескольких языках × нескольких вариантах, число копируется в каждый и обновляется не везде; ни даты, ни источника у него нет.
- *SQLite/БД под структурированные факты.* Против [ADR-0002](0002-no-embedder-pure-karpathy.md) и практики [ADR-0018](0018-finance-module.md): теряется git-diff-ревьюабельность каждого хода и append-only-аудит, ради запросов, которых на объёме одной карьеры не бывает.

**Следствия.**

- Построить: `src/ingest/career/types.ts` (zod-схемы + `i18nText`); append/guard-механику НЕ копировать из `finance/ledger.ts`, а параметризовать существующую каталогом и картой схем; импортёр снапшота `career-evidence.sh` → `metric(source: evidence)`; валидатор (`missing_translation`, `unknown_metric`, `literal_number_in_text`, `evidence_stale`, непроверяемая `business`-метрика); скоринг + рендер (Node-side, без сети и браузера — по образцу [ADR-0025](0025-finance-visualization-render.md)); интент-протокол и диспетчер карьерных операций.
- **`scripts/career-evidence.sh` обязан эмитить стабильный `snapshot_id` и машиночитаемый вывод — сейчас не эмитит.** На `snapshot_id` держатся три механики этого ADR (`metric.evidence_ref`, `variant.evidence_version`, предупреждение `evidence_stale`), а скрипт сегодня печатает markdown в stdout без идентификатора и без структурной секции — сослаться не на что, пин к версии evidence нереализуем, расхождение метрик не с чем сравнить. Требование: (1) снапшот **сохраняется файлом** в `raw/career/`, имя несёт `snapshot_id`; (2) `snapshot_id` детерминирован (дата снятия + хеш содержимого — повторный прогон без изменений даёт тот же идентификатор, иначе `evidence_stale` будет срабатывать на пустом месте); (3) рядом с человекочитаемым markdown отдаётся JSON с теми же числами (`{ snapshot_id, taken_at, metrics: [{ key, value, unit, as_of }] }`), из которого импортёр строит `metric(source: evidence)` — парсить markdown regexp'ом мы не будем. До этого шага импортёр evidence не пишется.
- **В `TelegramClient` отсутствуют `editMessageText`/`editMessageReplyMarkup` — их надо добавить в транспорт** ([ADR-0023](0023-telegram-transport-media-and-callbacks.md)): без них кнопочное редактирование плодит новые сообщения вместо правки одного, и диалог правки характеристики становится нечитаемым.
- Усложняется ввод: факт вводится один раз, но структурно — «просто дописать строчку в резюме» больше нет; достижение с числом требует завести `metric`; двуязычие удваивает текстовые поля (диктовка → формулировка движком → подтверждение).
- Теперь нельзя: хранить значения контактов и идентифицирующих ссылок в репо; писать числа в текст; ослаблять санитайзер ради удобства; заводить фиктивные места работы и поля под них; править `evidence`-метрики руками; молча резать буллеты при рендере.
- Границы репо: `raw/career/*.jsonl` — приватный репо; публичный держит схемы, валидатор и рендер. Отрендеренные документы (в них подставлены контакты) — вне обоих репозиториев, под gitignore.
- Проактив по карьере — только под существующий артефакт или назначенное событие (назначенный follow-up, реальное собеседование). Ритуальные recurring-напоминания не воспроизводим.
