# Подсистема «Поиск работы» — что она умеет и как этим пользоваться

Три части одной системы: **конструктор резюме**, **реестр целевых компаний с площадками**,
**воронка откликов с отчётностью**. Всё живёт внутри второго мозга: данные — append-only JSONL в
приватном репозитории, ввод — через Telegram-бота или CLI движка, тяжёлые артефакты (документ
резюме, дашборд, выгрузки) — локальные файлы и локальный сервис.

Решения зафиксированы в [ADR-0028](adr/0028-career-data-module.md),
[ADR-0029](adr/0029-company-discovery-and-network-access.md),
[ADR-0030](adr/0030-jobsearch-funnel-reporting.md),
[ADR-0031](adr/0031-hh-channel.md) (канал hh),
[ADR-0033](adr/0033-platform-registry-and-vacancy-identity.md) (реестр площадок),
[ADR-0035](adr/0035-ledger-single-write-path.md) (единственный путь записи); язык — в
[глоссарии](jobsearch-domain-glossary.md). Этот файл — про то, как оно работает на практике.
Схема конкретного хранилища (полки, реестр площадок как страницы вики, спецификация леджеров) —
в его собственном `CLAUDE.md` ([ADR-0032](adr/0032-storage-self-contained-schema.md)); этот файл
её не дублирует, а описывает функционал с точки зрения движка.

## 1. Что работает, что требует настройки, чего нет

Разделение честное: «написано и покрыто тестами» и «доходит до пользователя» — разные вещи.

### Работает end-to-end

| Возможность | Как пользоваться |
|---|---|
| Ввод карьерной базы: профиль, позиции, достижения, метрики, навыки, образование, языки, проекты, ключи контактов | диктуете боту, он эмитит интент |
| Правка: порядок, статус варианта, короткие поля, переводы | боту же; повторный ввод с тем же id — это правка |
| Включить/исключить достижение в конкретном варианте | кнопками под списком (`query achievements` с `variant_id`) |
| Импорт машинного замера в метрики | `pnpm career:evidence` |
| Чеклист справочника: чего не хватает, чтобы резюме собралось | `pnpm career:directory` или `query directory` боту |
| Предпросмотр варианта: что войдёт, что выпало и почему | `query preview` боту |
| Сборка резюме в файл | `pnpm career:render <variant_id>` |
| Реестр компаний: завести, поставить вес | боту (`add_company`, `set_fit_rank`) |
| Список компаний: отсев по гейтам, сортировка по весу с объяснением, оговорка о покрытии | `query companies` боту |
| Импорт официального экспорта LinkedIn | `pnpm jobsearch:import-linkedin <файл>` |
| Воронка: отклик, смена стадии, касание | боту (`add_application`, `add_event`) |
| Отчётность: JSON, дашборд, `.xlsx`, `.html` | `pnpm jobsearch:report`, затем `127.0.0.1:7788` |
| Проактив: напоминание о назначенном собесе, предложение follow-up | приходит само в дайджест-свип |
| Добавить площадку добычи/подачи (реестр + словарь) | страница `wiki/jobsearch/platforms/<id>.md` в хранилище + строка в `PLATFORM_IDS` (`companies.ts`); код-адаптер только при `search: dom-live`/`guest-api` |
| Записать в леджер воронки (`companies`/`opportunities`/`applications`/`application_events`/`form_answers`) с валидацией до записи | `pnpm jobsearch:append -- <ledger>` (строки из stdin или файла; §«Единственный путь записи») |
| Проверить все леджеры на пропуски мимо валидации | `pnpm jobsearch:validate` (exit ≠ 0 при любом пропуске) |
| Проверить вику целиком: орфаны, битые ссылки, реестр площадок ⊆ словарь, выжимки без концепций | `pnpm wiki:lint [--skills <dir>]` |
| Узнать, что пора повторить в учебном контуре (лесенка Лейтнера) | `pnpm learn:due` |

### Требует однократной настройки

- **`career-directory.local.json`** — имя владельца, значения контактов, отображаемые названия
  организаций и учебных заведений, URL. Форма — `career-directory.example.json`; какие
  именно ключи нужны под вашу базу, скажет `pnpm career:directory`. Файл лежит рядом с
  приватным контентом и **не** попадает ни в один репозиторий.
- **`REPORT_TOKEN`** в `.env` — без него сервис отчётности не стартует. Это намеренно:
  loopback защищает от сети, но не от локального браузера.
- **`CAREER_AUTHORS` / `CAREER_ROOTS`** — для замера по локальным git-репозиториям. Скрипт
  не хардкодит ни авторов, ни пути, чтобы они не оказались в публичном репозитории.
- **Перезапуск моста** после сборки: карьерный и воронковый протоколы попадают в системный
  промпт при старте процесса.

### Канал `web_search` заморожен — это решение, не забытый хвост

Канал `web_search` из каналов добычи компаний (`COMPANY_SOURCES`) **не работает, и это осознанно
принятое ограничение регрумминга 2026-09**, а не пункт, который забыли доделать. Формулируется
явно, потому что до этой правки статус читался как «пока не подключено» — а это «подключать
не будем в этой фазе».

Модуль загрузчика `src/bridge/net/fetcher.ts` готов и покрыт офлайн-тестами (allowlist,
перепроверка редиректов, robots, rate-limit, потолок размера, «никогда не бросает»),
детерминированный парсер страницы `parseCompanyPage` тоже. Но **вызывать их некому**: routine
`jobsearch-discovery`, которую [ADR-0029](adr/0029-company-discovery-and-network-access.md) §7
описывает как один пакетный прогон в сутки, не написана, и её реализация в объём регрумминга
не входит.

**Практическое следствие: леджер вакансий (`opportunities.jsonl`) через этот канал не
заполняется вовсе** — 0 записей с `company_source: web_search`, и это ожидаемое число, не
дефект данных. Компании заводятся **вручную, импортом файла и живым поиском по площадкам
реестра** (hh, LinkedIn) — трёх каналов из четырёх достаточно для точечного поиска, ради
которого подсистема и делалась.

Что нужно, чтобы разморозить канал, расписано в [ТЗ на S9](jobsearch-s9-discovery.md); это
следующая задача, а не открытый вопрос текущей.

### Площадки — реестр в хранилище, словарь в движке, не проза в скиллах

С [ADR-0033](adr/0033-platform-registry-and-vacancy-identity.md) площадка — не факт, размазанный
по трём полям и прозе двух скиллов, а сущность: одна страница реестра на площадку плюс одна
строка словаря. Правило источника истины простое и двустороннее:

- **Механика площадки** (как искать, как подавать, ловушки, датированные решения — например всё,
  что раньше в этом файле было прозой про hh: `search_field=name`, перебор специализаций,
  гео-очередь, сверка `total`/`declared`) живёт **в теле страницы реестра**
  `wiki/jobsearch/platforms/<id>.md` в хранилище. Этот гайд её не дублирует — здесь только
  инвариант, который не относится к конкретной площадке.
- **Замкнутый словарь id** — `PLATFORM_IDS` в `src/ingest/jobsearch/companies.ts` движка:
  `hh`, `linkedin`, `ashby`, `greenhouse`, `lever`, `join`, `smartrecruiters`, `workable`,
  `icims`, `site` (длинный хвост карьерных страниц), `email`. `pnpm wiki:lint` проверяет реестр
  ⊆ словарь и обратно — расхождение (страница без строки словаря или строка без страницы)
  считается находкой lint'а, а не «допилим потом».
- **Добавить площадку** = одна страница реестра + одна строка в `PLATFORM_IDS`; ADR больше не
  нужен ([ADR-0029](adr/0029-company-discovery-and-network-access.md) D4 в части «только через
  ADR» снят). Код-адаптер (`src/ingest/jobsearch/platforms/<adapter>.ts`, по образцу `hh.ts`)
  нужен только площадке с `search: dom-live` или `guest-api` — ATS с обычной формой заявки
  обходятся без кода.

**Инвариант hh, который остаётся фактом кода, а не страницы реестра:** публичный API закрыт
(`GET https://api.hh.ru/vacancies` отвечает `403` и на честный `User-Agent`, и на
`HH-User-Agent` без токена приложения — проверено 01.09.2026), а ходить в закрытую ручку с
куками живой сессии владельца запрещает [ADR-0009](adr/0009-tos-safe-engine-access.md). Поэтому
канал устроен так: страницу выдачи открывает человек или агент в Chrome
(`mcp__claude-in-chrome__*`), адаптер `hh.ts` снимает фиксированный набор полей по `data-qa` с
уже отрисованного DOM — ни одного HTTP-запроса от кода к hh не уходит. Извлекатель привязан к
чужой вёрстке и обязан падать громко: **ноль карточек при непустой выдаче — это поломка
прогона, а не «сегодня ничего не нашлось»**. У hh в реестре — точка отсечения `since: 2026-09-01`
(`wiki/jobsearch/platforms/hh.md`): конверсия по каналу считается только с неё, чтобы
незанесённые исторические отклики не портили воронку.

## 2. Быстрый старт

```bash
cd ~/llm-wiki && pnpm build
```

1. **Заведите профиль и первую позицию** — просто скажите боту, что вы делали и где. Он
   предложит формулировки и запишет только после вашего подтверждения: длинные тексты
   система за вас не сочиняет.
2. **Снимите замер:** `CAREER_AUTHORS='вы@example.com' CAREER_ROOTS="$HOME/projects" pnpm career:evidence`.
   В метрики придут коммиты, репозитории, объём кода и охваченный период — с датой и ссылкой
   на снапшот. Повторный прогон без изменений ничего не пишет.
3. **Посмотрите, чего не хватает:** `pnpm career:directory`. Он посчитает нужные ключи из
   вашей же базы и назовёт незакрытые.
4. **Заполните справочник** по образцу `career-directory.example.json`.
5. **Соберите резюме:** `pnpm career:render`. Документ ляжет в `~/career-render/` — вне обоих
   репозиториев, потому что в нём подставлены реальные контакты.

## 3. Как это устроено с точки зрения пользователя

### Резюме собирается из фактов, а не пишется заново

Число живёт ровно в одной записи-метрике, а в тексте достижения стоит плейсхолдер
`{{metric.<ключ>}}`. Обновили метрику — обновились все варианты резюме сразу, и у числа
есть дата и происхождение. Поэтому:

- **Числа в тексте достижения — предупреждение.** Система заметит «30 %» прямо в буллете и
  скажет, что его место в метрике. Годы и версии (`2024`, `HTTP/2`) она не трогает.
- **Метрика из замера правится только пересбором замера.** Не согласны с числом — заведите
  своё, класса `business` (тогда обязательно ответить, подтверждается ли оно внешне) или
  `manual` (оценка; в документе она пойдёт с предупреждением).

### «Где нашёл» и «где подал» — два разных факта

Вакансия и отклик несут по [ADR-0033](adr/0033-platform-registry-and-vacancy-identity.md)
четыре поля из словаря площадок: `platform` (где вакансия найдена), `external_id` (id вакансии
на площадке, с буквенным префиксом без разделителя — `hh136857307`, чтобы санитайзер не принял
голое число за телефон), `url` (публичная ссылка без query) и `applied_via` (где отправлена
форма). «Нашёл в LinkedIn, подал через Ashby» — два проверяемых факта, а не один: склеенные в
одно поле, они дают неверную конверсию сразу по обеим площадкам. У истории (записей до
[ADR-0033](adr/0033-platform-registry-and-vacancy-identity.md)) все четыре поля опциональны —
читаются как есть; у новой записи через `pnpm jobsearch:append` они обязательны (кроме
`external_id` у `site`/`email`, где идентификатора вакансии не существует в природе).

Тот же факт «ссылка на вакансию» у вакансии называется `source_url`, а у отклика — `url`: два
имени одного и того же по историческим причинам ADR ([ADR-0029](adr/0029-company-discovery-and-network-access.md)/[ADR-0031](adr/0031-hh-channel.md)
закрепили `source_url`, у отклика поля не было вовсе, и [ADR-0033](adr/0033-platform-registry-and-vacancy-identity.md)
завело его как `url`) — пара названий одного факта разведена в
[доменном глоссарии](jobsearch-domain-glossary.md).

`company_source` — соседнее, но отдельное поле: как компания попала в воронку. Словарь
расширен площадками-агрегаторами (`hh`, `linkedin`) поверх прежних `manual`/`linkedin_export`/
`web_search`; значение `linkedin` легализовано — оно означает живой поиск в LinkedIn, а не файл
экспорта (это `linkedin_export`).

### Вариант — это выбор, а не файл

`variant` говорит, на каком языке, под какую роль, что закреплено и что исключено, и в какие
рамки резать. Один и тот же набор достижений даёт разные документы. Воронка ссылается на
вариант, поэтому вопрос «какой вариант конвертит» — считаемый.

### Ничего не выпадает молча

Если буллет не влез в лимит, он попадает в список выброшенного с причиной и баллом.
Если чего-то не хватает — документ не собирается вовсе и печатается перечень проблем.
Половинчатое резюме уходит рекрутеру незамеченным, поэтому лучше не выдать его совсем.

### Контакты через бота не проходят физически

Скажете боту телефон или почту — он их не запишет, и это не каприз: маскер на пути записи
превращает их в `[REDACTED:phone]` ещё до движка, и ослаблять его нельзя, он защищает всю
вику. Бот заводит только **ключ** контакта; значение вы вписываете в справочник, и оно
появляется ровно в одном месте — в отрендеренном документе.

### Стадия отклика не хранится, а вычисляется

Вы записываете **события** («ответили», «позвали на интервью»), а стадия выводится из них.
Поэтому отчёт умеет отвечать на «когда пришёл первый ответ», «сколько было раундов»,
«отказали до или после тест-задания» — по полю статуса такие вопросы неотвечаемы.

**Касание — не переход.** «Написал рекрутеру» записывается, но стадию не двигает и в
конверсии не входит: иначе переписка рисует себе конверсию сама. И таймер молчания
работодателя оно не сбрасывает — три письма в пустоту не отменяют тишины.

**`ghosted` ставите вы, а не система.** Молчание — это отсутствие события, а не событие;
компания может ответить и на шестидесятый день. По таймауту приходит предложение с кнопками,
и «Считать игнором» — единственный способ, которым `ghosted` попадает в данные.

### Отчёт не даёт себе соврать

Процент никогда не показывается без числа наблюдений: `18 % (4 из 22)`. При `n < 100` рядом
идёт доверительный интервал, при `n < 10` в разрезе показываются только абсолютные числа,
при `n < 30` тренды не рисуются вовсе. Пустой знаменатель — прочерк, а не «0 %». Внизу
дашборда стоит оговорка, что показатели покрывают только подключённые источники: полного
среза рынка не существует.

### Напоминания приходят только под запись

Ритуальных «раз в неделю обнови профиль» здесь нет и не будет — предыдущий набор таких
напоминаний был отключён именно потому, что они рапортовали о процессе, под которым не было
ни одного артефакта. Осталось два триггера: назначенное собеседование (за сутки и за два часа)
и молчащий отклик. Сказать нечего — система молчит.

## 4. Команды

| Команда | Что делает |
|---|---|
| `pnpm career:evidence` | замер по локальным репозиториям → метрики `source: evidence`; идемпотентно |
| `pnpm career:directory` | чеклист ключей справочника, посчитанный из базы; ненулевой код выхода, если чего-то нет |
| `pnpm career:render [id] [--out путь]` | собрать вариант в документ вне репозиториев |
| `pnpm jobsearch:import-linkedin <файл> [--dry-run]` | импорт официального экспорта: запись на компанию, дедуп по домену |
| `pnpm jobsearch:report` | сервис отчётности на `127.0.0.1:$JOBSEARCH_REPORT_PORT` |
| `pnpm jobsearch:append -- <ledger>` | строки из stdin/файла → валидация схемой **до** записи → пачка всё-или-ничего → readback в stdout; единственный легальный способ дописать `companies`/`opportunities`/`applications`/`application_events`/`form_answers` ([ADR-0035](adr/0035-ledger-single-write-path.md)) |
| `pnpm jobsearch:validate` | проверяет все леджеры разом; ненулевой код при любом пропущенном мимо схемы месте |
| `pnpm jobsearch:migrate` | миграция полей площадки на существующих записях: **dry-run по умолчанию** (отчёт в stdout), `-- --report path.txt` — тот же отчёт ещё и в файл, `-- --apply` — запись |
| `pnpm learn:due` | детерминированный список «что пора повторить» по лесенке Лейтнера из журнала `raw/learning/reviews.jsonl` — LLM арифметику дат не делает |
| `pnpm wiki:lint [--skills <dir>]` | детерминированные проверки хранилища: орфаны, `[[wikilinks]]`, битые ссылки, страницы без frontmatter, невалидные записи леджеров, реестр площадок ⊆ словарь и обратно, выжимки без концепций; с `--skills` — ещё и пути к переехавшим полкам в скиллах |

Эндпоинты сервиса (все GET, все read-only): `/api/stats`, `/dashboard`, `/export.xlsx`,
`/export.html`. Ссылку на дашборд удобно открывать с одноразовым `?t=<токен>` — он
обменивается на httpOnly-cookie и снимается редиректом, чтобы не оседать в истории браузера.

## 5. Что бот понимает

Три протокола с разными тегами блоков, поэтому финансовый, карьерный и воронковый ходы не
мешают друг другу — два блока в одном ответе применяются оба.

**Карьера:** `add_profile`, `add_position`, `add_achievement`, `add_metric`, `add_skill`,
`add_education`, `add_language`, `add_project`, `add_contact`, `remove` (с `entity`),
`toggle_achievement`, `reorder`, `set_status`, `set_field`, `create_variant`,
`query` (`positions` · `achievements` · `variants` · `skills` · `metrics` · `preview` · `directory`).

**Воронка:** `add_company`, `set_fit_rank`, `add_application` (несёт опциональные `platform` /
`external_id` / `url` / `applied_via` — §3 «Где нашёл» и «где подал»), `add_event`,
`query` (`funnel` · `applications` · `companies`).

Правка — это повторный ввод с тем же идентификатором: данные append-only, побеждает поздняя
запись, а история остаётся. Удаление — тоже запись, а не пропажа строки.

## 6. Границы, о которые вы споткнётесь

- **Фиктивных мест работы нет и не будет.** Полей под «компании-доноры» в схеме нет; знание
  о приёме лежит в `knowledge/` как чужой метод. Честная замена — строка-описание компании
  рядом с названием и акцент на масштабе систем.
- **Движок без сети.** Он не ищет вакансии сам; сеть живёт в отдельном слое моста за
  allowlist доменов — и, как сказано в §1, канал `web_search` заморожен решением, а не
  недоделан.
- **Никакой автоматизации откликов и коннектов.** Система готовит и ранжирует, отправляет
  человек.
- **Корпоративная инфраструктура работодателя под это не используется.**
- **Механика конкретной площадки (LinkedIn, hh и остальные девять) — не здесь.** Ловушки вроде
  шага пагинации гостевого API LinkedIn или `geoId` живут в теле её страницы реестра
  `wiki/jobsearch/platforms/<id>.md` в хранилище (§1 «Площадки»), а не в этом файле — второй
  копии той же прозы в движке решением [ADR-0033](adr/0033-platform-registry-and-vacancy-identity.md)
  больше нет.

- **Отрендеренные документы и справочник контактов — вне обоих репозиториев.** Попытка
  записать документ внутрь репозитория обрывается с ошибкой до записи, а не после.
